# 设计：成员会话的「机构级能力」边界（跑 51 残余第 4 条）

> 状态：**已裁决，未实现**。本文只定方向与验收口径，代码在下一轮落地。
> 产生它的实测：`docs/acceptance/phase12-v5r-rules-conformance.md` §93.2 第 4 条、§96.5。

## 1. 实测到的事实（不是推断）

- 成员回合在**激活投递**下跑在一个**独立内核实例**里（跑 51 的 transcript：成员侧 `eligible` 三席、`m1`、票箱 `b-1` 全都不存在）。
- 于是提示词教它调用的机构级动作被拒：`vibe_v5_verdict(target="b-1-…")` → `VMU_NO_SUCH_OBJECT`；
  `vibe_v5_poll_vote` → `no member "r-1" on this roster`。
- 这些拒的**名字是错的**：它们说的是「这个 id 不存在」，实际原因是**这个会话根本没有机构状态**。
  一个错名字比没有名字更坏 —— 读到它的人会去修 id。

## 2. 裁决：以「作用域」为第一等概念，用 pack 声明 + 现有窄面机制表达

不桥接子内核。理由：桥接要新增请求/响应协议、权限、超时与失败语义（一套新机制），
而它要解决的问题在**语义上**已经有答案 —— 成员本来就不该行使机构级动作，
成员的正规通道是 ①回复字段 ②自己成果库里的记录 ③消息/收件箱。

落地三件（缺一即不成立）：

1. **声明（pack）**：`packs/v5r/member-scope.js` 导出 `TOOL_SCOPES`，把 41 件 pack 工具逐条标 `office` / `member` / `both`，
   并导出由它**派生**的 `MEMBER_SAFE_TOOLS`、`OFFICE_ONLY_TOOLS`（不许手抄第二份清单）。
2. **收窄（机制）**：交付成员回合时把成员的可用工具面设成 `MEMBER_SAFE_TOOLS`
   （既有 seam：`vibe_vmu_turn.tools` → `setMemberToolOverride`；跑 51 已证明窄面生效：成员会话 0 次宿主工具）。
3. **提示词（文本）**：成员提示词里「你能调用什么」的清单**从同一份声明派生**，不另写；
   并加一句边界说明：机构级读数在推动者的内核里，成员要它们只能通过回复字段/消息请求。

## 3. 验收口径（门禁，做成可执行断言）

- `tests/audit-member-scope.test.mjs`（新）：
  - 每件 pack 工具都有作用域（`Object.keys(TOOL_SCOPES)` 与工具目录**双向**一致，缺一即红）；
  - `MEMBER_SAFE_TOOLS ∩ OFFICE_ONLY_TOOLS === ∅`，且两者并集 = 工具目录；
  - 成员席位真正收到的窄面 = `MEMBER_SAFE_TOOLS`（用既有的窄面读数断言，不是读源码字符串）；
  - 成员提示词的工具清单与 `MEMBER_SAFE_TOOLS` **逐条相等**（排序后比较）。
- 真机：下一次跑时成员若尝试机构级动作，必须是**不可见**（不在窄面内）而不是「被拒」；
  若仍出现 `VMU_NO_SUCH_OBJECT`，说明窄面没盖住，按缺陷计。

## 4. 明确不做

- 不做「成员调用机构级工具时改名为 `VMU_SESSION_SCOPE`」：窄面成立后这条路径不可达，
  给不可达路径写新拒码违反「没有消费者就没有机制」。等真的出现泄漏再补。
- 不在本设计里动 `vibe-mat*` 系列 legacy 预设（用户已裁定不在范围内）。

## 裁决 B（用户，m21840）：成员真跑 + 所办代记

**决定**：成员仍以真子代理运行（各自独立的内核实例），研究所记录本由**所办代数登记**。
不做 A（全所共用一本记录本），不做 C（弱化测试）。

### 这个决定在机制上意味着什么

B 不是"什么都不改"，它要求三条都在位，否则成员的动作仍然静默失效：

1. **子侧声明**：成员仍然可以在自己的（私人）记录本上写卡、开会，但那不是研究所的记录本。
   所以"成员能调什么"必须**声明**清楚，并且当一条调用只落在私人实例上时，
   回执不得读作"已登记进研究所"。实现方向：把"写研究所状态"的面孔在 `packs/v5r/member-scope.js`
   里标出，子侧调用时回执带上 `landsIn: 'member-private-kernel'`（而不是静默 ok）。
2. **所办侧代记**：成员的产出必须有一条**到达研究所记录本**的路，且由**框架**执行而不是靠所办记得：
   成员的回复（回执文本）里带的声明字段，在 turn 结算时由**所办侧**应用到**所办内核**，
   并记为 `owner = <该成员>`。这条路的入口是 `vibe-math-vmu/kernel/turn/index.js` 的字段应用路径，
   不是提示词纪律。
3. **提示词契约**：成员必须被告知"你的记录本是草稿本，正式登记由所办按你的回执代记"；
   所办必须被告知"你是登记人"。否则成员会以为自己在登记，所办会以为自己不需要动手。

### 实测证据（为什么必须走 B 而不是"保持现状只是改测试"）

- 真子代理运行（`_oneoff/vm-slv/full-1025-164255.jsonl`）里，研究所记录本共 **12 条记录，owner 全部是 `member-1`（所办）**，
  没有一条来自被派遣的成员——成员的写入落在自己的实例里。
- 子会话的 session 日志是**只有 header** 的单行文件（零事件），说明子侧确实是独立实例、其状态不回流父侧。

### 实施状态（诚实边界）

**本轮只落了裁决与本文件**。上面 1/2/3 三条**尚未实现**，因此"成员登记会到达研究所记录本"这一结论
在本轮**不成立**；下一次真机验收不能据本文件宣称该能力已具备。

### 门禁计划（实现时同步落地）

- 子侧声明：断言子模式下一件"写研究所状态"的面孔调用，回执带 `landsIn` 而非裸 `ok:true`。
- 代记：构造一个成员声明字段，断言父内核 records 里出现 `owner = 该成员` 的条目，且回执列出 `filed`。
- 提示词：断言成员座位文本里出现"草稿本/所办代记"契约，所办文本里出现"你是登记人"。

## 实现路径修正（第 9 轮，源码级核实）

上一节给 B 列了三条机制。源码级核实后，其中**第 2 条（所办代记）不需要新增框架能力**，
只需要把既有能力写进双方契约——这缩短了实现面，也避免造第二条写卡路径：

- `vibe-math-vmu/packs/v5r/tools.js:1158` —— `gatedCardHandler()` 里 `const by = has(args.member) ? str(args.member) : null`；
  `by` 就是卡的作者（owner）。也就是说**所办调用 `vibe_v5_record_proposition { member:"<成员id>", … }` 时，
  登记出来的卡 owner 就是那位成员**，而不是所办自己。代记通道**已经存在**。
- 同一路径的写卡仍然经过 `singleWriter`（`:1175`）与 p1 证据闸，因此"代记"不会绕开"一个命题只有一条写路径"的约束。

因此 B 的剩余实现面缩小为三件事：

1. **契约文本**：成员座位文本必须写明「你的记录本是你自己的草稿（真子代理模式下是私有实例），
   研究所的正式记录本由所办登记；要立项就把卡片素材写进回执，由所办代记」；
   所办文本必须写明「每收完一位成员的回执，用 `vibe_v5_record_proposition { member } ` 代记，owner 是该成员」。
2. **子侧声明**（可选、诚实优先）：成员的私有登记回执若能被标注为"只落在私有实例"更好；
   在拿到可读的子侧信号之前**不假装**（不写 `landsIn`，只靠契约文本，避免造出读不到的字段）。
3. **门禁**：断言 ①代记通道的 owner 归属（office 传 `member` ⇒ 记录 owner = 该成员）；
   ②两段契约文本在装配后的提示词里真实存在（不是只写在文档里）。
