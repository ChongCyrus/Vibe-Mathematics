# vmu 26 · 整轮编排（Turn Orchestration）

> 状态：**设计（轮 337）＋ v1 实现（`kernel/turn/index.js`）** ✓
> 定位：★★★ **goal 的首要目标** ✓ —— 把**原 vibemath-v5r 的整轮运行机制**（成员回合：**提示词装配 → 投递 → 回复解析 → 分派到内核面**）搬到 vmu 侧，**使 vmu 自己就能跑出一轮研究所** ✓。

## 0. 一句话总纲

**一轮 ＝ 一次"装配→投递→解析→分派"** ✓，其中：
- **装配**由 **`vmu.prompt` 管线**完成（**提示词是数据** ✓，段可注册、可覆盖、可按 role/phase/member/task 绑定、可快照 ✓）；
- **投递**走**适配器缝**（宿主/子代理/LLM 都由注入决定 ✓，**没有适配器就具名拒** ✗，绝不假装成功 ✓）；
- **解析**按**字段目录**严格校验（围栏 JSON ✓，未知字段具名拒 ✓）；
- **分派**把每个字段交回**拥有它的内核面**（同一字段永不由两个面处理 ✓）。

> ★★ **本卷要教的 API（★ 轮 501 补 ✓）**：★ **`createTurnOrchestrator({ sectionPolicy, noticeBlock, bus, … })`** ✓ —— ★ **回合编排器工厂**；★ **它返回的正是 §2 那五步**（`open`／`assemble`／`deliverTurn`／`parse`／`apply` ✓）。★★ **另有 `extractFence`** ✓（★ 从回复里取出围栏 JSON ✓）、**`FIELD_OWNERS`** 与 **`resolveOwners`** ✓（★ 每个字段归哪个面所有 ✓ —— ★ 这就是"面表"的真源 ✓）。

## 1. 为什么"编排"必须也在框架里（而不是留在原预设）

★★ 原预设的运行机制**自带一套循环** ✓（`charterFor`／`briefBlock`／`replySpec`／`initialPrompt` ＋ 逐成员逐轮推进 ✓）。**只搬工具、不搬循环**的结果是：**能力面覆盖了，但"谁来跑"仍是原代码** ✗ ⇒ **一旦宿主只装 vmu，研究所跑不起来** ✗。
**所以本卷的目标是**：**循环本身成为框架的一个面** ✓ —— 于是 **vmu 侧可以独立跑** ✓，且**每一步都可被 settings／中间件／pack 调控** ✓。

## 2. 五个阶段与它们的归属（**逐条可判定** ✓）

| 阶段 | 做什么 | 归属 | 失败时 |
|---|---|---|---|
| **① 打开回合** | 记下"谁、第几轮、什么任务、什么阶段" | `turn.open` ✓ | 缺 member／phase ⇒ **具名拒** ✗ |
| **② 装配** | 由**管线**拼出该成员这一轮该看到的文本（含章程、契约、包段、叠加） | **注入的 `vmu.prompt`** ✓ | **管线未接线 ⇒ `VMU_ENGINE_UNAVAILABLE`** ✓（**绝不自己拼** ✗） |
| **③ 投递** | 把文本交给该成员，取回它的回复 | **适配器缝**（`deliver` ✓） | **无适配器 ⇒ 具名拒** ✓ |
| **④ 解析** | 从回复里取出**围栏 JSON**，逐字段校验 | `turn.parse` ✓ | 无围栏／非法 JSON ⇒ **具名拒** ✓；未知字段按 `vmu.turn.unknownReplyFieldMode`：默认 `ignore-named`（已知字段照常、未知字段进 `reply.ignoredFields`＋一条 notice），`refuse` ⇒ **具名拒** ✓ |
| **⑤ 分派** | 每个字段交给**拥有它的面**执行 | **面表**（`plan`／`apply` ✓） | 面缺失 ⇒ **记账为未执行**，**不静默丢弃** ✗ |

★ **确定性**：**同一输入 ⇒ 同一装配字节**（由管线保证 ✓），且 **`plan()` 是纯函数** ✓ ⇒ **整轮可快照、可比对** ✓（这正是"逐轮 A/B"的前提 ✓）。

## 3.1 ★★★★ 逐成员装配：靠管线的【模板变量】，不靠写死文本（轮 341）✓✓

★★ **闭合方式（零硬编码** ✓✓）：**管线本来就支持模板变量** —— 段的文本里可写 **`{{ member }}`／`{{ role }}`／`{{ phase }}`／`{{ time }}`／`{{ pack }}`／`{{ task }}`／`{{ setting:键 }}`／`{{ count:键 }}`** ✓（**白名单**：**未登记的变量【具名拒**】✓；**值里的模板语法会被转义**，**值不可能注入占位符** ✓）。

⇒ **所以补的是一个【角色段】，不是一堆每人一份的文本** ✓✓：

```
【本轮面向的成员】代号：{{ member }} ｜角色：{{ role }} ｜阶段：{{ phase }}
★★ 分派决定做什么，判断属于你自己（v5r 的既有分工）。
```

★ **循环负责把 `role` 传下来** ✓（`open({ member, role, phase })` ✓ ⇒ `assemble` 透传给管线 ✓）⇒ **两个成员自然得到不同文本** ✓✓，**且一个人可以改 settings／config／中间件就换掉它** ✓。

## 3.2 ★★★★ 唤醒策略与多轮驱动：**"vmu 自己跑多轮"**（轮 347 设计）✓✓

★ **为什么必须有这一节** ✓：**上一轮实测**证明**原预设【自己不做编排**】✗ —— `nudge` 被接受却**不排任何可续子任务** ✓，**"唤醒谁／何时／以何提示词"全交给宿主** ✓ ⇒ ★★ **框架若只做"单轮"，就仍然需要一个宿主来管多轮** ✗ ⇒ **本节把"多轮"也做成框架自己的事** ✓。

**两条新增能力** ✓：

| 能力 | 契约 |
|---|---|
| **`nextTurn({ members, phase, round, recent })`** ✓ | **按策略给出【下一轮该唤醒谁】** ⇒ `{ member, role, phase, why, nextStep }` ✓；**没有可唤醒者 ⇒ 返回 `null`**（**不是编一个出来** ✗） |
| **`drive({ members, rounds, phase, deliver, faces })`** ✓ | **连跑 N 轮** ✓：每一轮都走 **装配 → 投递 → 解析 → 分派** ✓，**逐轮记账**，**任一轮失败即停并如实回报**（**绝不悄悄跳过** ✗） |

**策略来自 settings** ✓（**按纪律登记** ✓）：**`vmu.turn.wakeupPolicy`** —— `round-robin`（默认 ✓：按在册次序轮转 ✓）／`least-recent`（**最少被唤醒者优先** ✓，**同票按在册次序** ⇒ **确定性** ✓）✓；★ **`members` 为空 ⇒ 不唤醒任何人也【不报错**】✗✓（**"没有人可唤醒"是合法状态** ✓，与"失败"分开 ✓）。

**三个不变量** ✓：
1. **纯函数性**：`nextTurn` **不改状态** ✓ ⇒ **同输入 ⇒ 同选择** ✓（**可快照、可对拍** ✓）；
2. **有界**：`rounds` 必须**显式给出**（**不设"无限循环"默认** ✗）✓；
3. **不静默**：**轮次失败 ⇒ 停止并回报该轮编号与前一轮的收据** ✓（**不吞错、不假装跑完** ✗）。

## 3.3 ★★★★ tick 缝：**三个问题、三个归属**（轮 348）✓✓

## 3.41 ★★★★★ 同源块的“收窄/sticky/不继承”与 `toolPresentation`（PHASE 9+ / G7）

★ **单一来源**：块里的名字集合来自 `out.tools` 的 **`effectiveNames`**，与 wire 是同一次计算；native/ptc 只换描述，不另算名字（§3.39）。
★ **只许收窄，不许变宽（sticky）**：`tools.allow` 只能把本回合的 wire 收窄到 allow 交集；回合结束后 override 清除，**下一回合恢复角色面**。`tools.allow` 里出现未注册名 ⇒ **具名 `VMU_INVALID_ARGUMENT`**，该回合不执行（`tools/turn.js` 的 allow 校验）。

★ **`toolPresentation` 与 `promptAck`**：
- `toolPresentation` 是**声明通道**：pack 声明“本机构以 native / ptc / defer 呈现”；**非 native 必须带 marker**（例如 `【本轮工具呈现｜<slot>】`），否则宿主不改写；
- **native**：逐字保持原块（`【本轮你实际能调用的工具｜…】… 与你这回合的 wire 完全一致 …`）；
- **ptc 已应用**：wire 换成 `run_code`，块改为 `【本轮工具呈现｜<slot>】本回合以 run_code 呈现：下列 N 个工具可通过代码调用…（它们不在 wire 顶层目录里，这是呈现方式的差异，不是收窄）`；**marker 必须在**，否则调用方无法区分“收窄”与“呈现方式变化”；

- **v5r 不声明 `toolPresentation`**，所以 v5r 的块逐字是 native 形状（`与你这回合的 wire 完全一致`）。

★ **判据**：成员会话 `block` 与 `request/header.tools` 名字集合一致；root 会话的 `block` **不得含 `｜member】`**；`slv-inspect` 0 RED 才是通过。

2. **id 不复用**：`turn` 的逐轮记账若引用 `t-N`/`mt-N` 之类的 id，恢复后必须仍然指向同一个对象。id 一律经 `kernel/ids.js` 的 `mint(kind, prefix)` 铸造（计数器耐久、恢复取 `max(已观测)+1`）；**不许**再新造 `let seq = 0`（内核约 30 处已由 vmu-core 批量替换；`tasks.js` 有意保留**每实例**计数并靠 `snapshot()/restore()` 恢复——理由见报告）。
3. **快照只装状态，不装接缝**：面侧 `snapshot()` 的 `data` **不得**包含注入的宿主接缝（`deliver`/`wake`/`bus`/`clock`/`timer`/`spawn`/`fetch`）；`restore()` 必须把它们列回 `skipped[]` **或在接口里明确不算**（本仓采用后者：**接缝由内核重新注入，不算 skipped**）。
4. **可观测的诚实**：恢复后若某个面**没水合**（无 adapter／无 restore seam／journal 有洞／**回放抛错**／面返回 `{ok:false}`／**键下不是投影信封**），`resume.status().projection.degraded=true` 且 `unhydrated[]` 具名 —— **"重启后空名册"与"真的恢复了"必须可区分**，编排面不得据此继续当作正常轮次。

**Round 5 增补（任务板的两条图保证也在恢复面成立）**：
- **DAG 在写入时强制 ⇒ 恢复出的板必然无环**：依赖边只经 `tasks.create()` 的 `deps` 与 `tasks.setDependencies()` 落库，两条路都过环检测，自环/整图环**具名拒** `VMU_TASK_DEPENDENCY_CYCLE` 并把**环路径**放进 `detail.cycle` 与 hint（编排面据此知道该删哪条边）。`unmetDeps` 的"开工时校验"语义**不变**。
- **写域 advisory 不是约束**：`writeScopes` 由任务创建者声明，规范化后随任务对象**一起投影**（`tasks.snapshot()/restore()` 自动携带），重叠只出现在 `status().writeScopeConflicts` 与 `list()` 行里；**永不阻断** claim/transition。⇒ 一轮编排看到一个重叠时，应把它当作"去和同事对一下"的信号，而不是一个错误。
- **诊断面**：`tasks.status()` 新增 `dag` / `writeScopes` / `writeScopeConflicts` 三个只读字段（F35/F39 的可观测面）。

**Round 3 增补（与人相关的"在途"也在耐久范围内）**：
- **人工审批的"在途"＝存取 `human` 键**：审批队列、否决台账、`pendingReason`（已承诺但尚未写下的理由）跨重启保留；`gate()` 重启后**仍拒**且复用**同一个** `requestId`（不会为同一动作开出第二个请求），id 计数器取 max+1。未接装配时，该面在 `unhydrated[]` 中具名。
- **状态型投影必须写穿**：`vmu.resume.writeThrough`（默认 `true`）—— 只挂 `faces{}` 而不 `attachProjection` 的 state 面是"可水合但从不写"，等于假持久；写穿失败计数可见（`status().writeThroughFailures`）。
- **`phase` 是引擎拥有的耐久值**：`resume.setPhase()`/`phase()`；装配侧仍需在相位变化点各接一行（未接 ⇒ 空投影 `present:false`，报事实不报错）。

**Round 4 增补（F18 锁 · F51 重启标记 · 未挂面结论）**：
- **恢复是独占段（F18）**：`createResume({lock})` 消费仓库自己的 `vmu.store.lock` 原语（`kernel/storepolicy.js:138/168`），`recover()` **在 `finally` 释放**（成功／早返回"无 store"／任何抛错三路都释放，用真 `createStorePolicy` 断言），并发第二个恢复 ⇒ 具名拒 **`VMU_RESUME_BUSY`**；`vmu.store.lock` 未声明时是零机制透传（`locked:false`，仍走 `finally`）。⇒ 多轮驱动不得让两次恢复交叠，按具名拒重试即可。释放失败**不静默**：`status().lock.lastError` ＋ log ＋（已登记的）`resume/lock-release-failed` 事件。
- **"我重启过"是耐久事实（F51）**：`status().restart` / `resume.restart()` = `{generation, restarted, at, reason, interrupted, unhydrated, readBack, phase}`，由耐久 `resume` 键的 `recoveries[]` 派生 ⇒ 编排面可用它区分"首跑"与"第 N 代续跑"，并看到重启代价（中断数、未水合面）。相邻标记：`work`（= v5r 的 `pendingWork`，带 `interruptedReason`）、`ids` 计数器、`human` 未批队列、Lean/mathjobs 的 `Formal/Jobs/<id>.json` 作业镜像。**v5r 的 `meetingOpen` 在 vmu 无等价物（具名缺口：需在会议投影里加"已开未收束"标记）**；`kernel/activity.js` 的 generation **有意不持久**（一次性、只对未来生效的等待器）。
- **未挂面结论**：`members`（单例、可挂，带 null 守卫）、`budget`（Round 4 补公共 `snapshot()/restore()` ⇒ 可挂）、`tasks`（journal）＋ reader-c 的 `meetings/ballots/ballotbox/minutes/chat/panel` 可挂；**`meeting`/`ballot` 是每实例工厂 ⇒ 单例投影不适用**（要跨重启挂 `meetings`/`ballotbox`，多实例需注册表——具名未做）；`mailbox` **自持久**，无需投影行。

- **重派缺失成员＝装配声明的策略（引擎只递名单＋计数）**：可复制配方——

**Round 8 增补（端到端钻取：恢复＋人工干预在同一场景里跑通）**：
- **一条可复制的钻取**：`tests/vmu-resume-e2e.test.mjs`（**63/0, exit 0**）在**同一个 store 文件**上连开三次"进程"，把"派活→留未读信→暂停→注入指令→续跑→动作被门拦下→重启→再重启"串成一条时间线。编排面可直接照搬的三组读数：① 重启后 `status().inflight` = `pending=1 / interrupted=[w-1(owner r-1, reason kernel-start)] / pendingNow=0 / unackedMail=2`；② `status().restart.generation` 逐代递增（1→2→3），`reassignAttempts['r-2']` 同样耐久（1→2→之后 `exhausted`，`maxAttempts:2` 用尽即**不再重派**）；③ 未批动作在**两次重启**之间**确实没跑**（板一直是空的），直到 `decide({ requestId, allow: true })` 之后**同一个调用**才成功，且复用**同一个** `requestId`、不产生第二个请求。
- **两条必须由装配做的动作（本轮具名缺口，框架不自动做）**：① **优雅退出时 flush journal**——`mode:'journal'` 无写穿，不 `resume.snapshot({ key })` 就整本留在内存里（`kernel/index.js` 目前没有这一步）；② **等写穿落地再"退出"**——写穿是异步文件 I/O，同 tick 重启会读到旧文件。两条在钻取里分别由 `quiesce()` / `settle()` 明确做出来，并各留了断言：`2i`（缺口本身：重启前该键仍是 `[]` 种子）、`2f/2g/2h`（写穿已落地：`writesThrough >= 5`、`writeThroughFailures === 0`、fold 里已有 `human`/`mailbox` 的 state 信封）。
- **三条恢复面规则**（journal 序列续接／先 state 后 journal／空种子数组按首跑）写在 docs/07 §16，每条都有"改之前真的错"的实测读数。
- **G7 正对照（跨面，供 `ballotbox`/`mailbox` 接耐用日志时引用）**：把 mailbox 绑到**真的** `createDurableCommitLog`（`kernel/ballot.js` 协议，宿主只提供 `append/readAll`）后复跑同一套形状 ⇒ **两条契约各自照旧**：state 面**仍自动写穿**（`9f`：`writesThrough >= 2`、`failures=0`；`9g`：fold 里已有 `mailbox` 的 state 信封且**未显式 `snapshot()`**）、journal 面**仍必须显式 flush**（`9h`→`9i`）；并且重启后 `9j` 的未读计数（1）来自 **state 投影**，而 `9k` 的提交日志同一时刻已 **settled** ⇒ **"提交耐久"与"投递/正文状态耐久"是两件事**，一句"已接耐久日志"不能替代另一件。

**Round 9 增补（退出契约落地 ＋ 多实例改判；`tests/vmu-resume-e2e.test.mjs` **81/0, exit 0**）**：
- **退出有了一个可断言的接缝**：引擎 `recovery.settle()`（排空在飞写穿）／`flushAll()`（刷 journal，state 键具名 skip）／`exit({reason})`（两半边，`ok` 取 AND，**失败进回执、不 throw**——因为它在宿主 dispose 路径上）；装配侧由 core 的 `kernel/index.js shutdown()` 调用。⇒ 编排面/宿主只需 `await kernel.shutdown({reason:'…'})` 并检查 `status().shutdown`；钻取 `10a`–`10k` 断言到"**一次 await 即耐久**"与"**下一位读者（另一个 store 实例）看得到**"，`10l` 断言**装配确实调了它**。
- **多实例不需要注册表，需要的是【被包裹的方法】**：`kernel/index.js` 的 `methodsOf` 只列了 `tasks`，其余声明为投影的面拿到 `[]` ⇒ 写穿永不触发 ⇒ `members/meetings/ballotbox/budget/chat/panel/minutes` **声明为投影却从未被写过**（钻取 `11c`：开两个会、`settle()` 后 `meetings` 键仍是 store 的 `[]` 种子；`11d`：退出 flush 按契约只刷 journal，**救不了 state 键**）。把方法列表填上（`['open','close','attend','motion']`）⇒ 写穿落地、**重启后两个会一起回来**（`11e`/`11f`）。⇒ 若一轮编排要"重启后接着开那个会"，缺的不是新机制，而是装配的条目。

## 附录：工具呈现（PHASE 8 / 目标 10）的两条实测结论

- ★ **`deferLoading` 是【延迟激活】标志，★ 不省略 schema。** 真机实测（v5r 声明十个 defer 面）：header 工具数 100 → 101、schema 字节 **102,114 → 102,883（+769）**；同一批 100 个共享工具 **102,013 → 102,162（+149）**；每个 defer 工具 **+20 字节**（正是该字段），且 `parameters` **仍完整在 header**（`vibe_v5_lean_run` 498 → 518、`hasParameters:true`）。⇒ **想靠 `defer` 省 wire 是错的**；它的价值只在"延迟激活"。★ 下一个想省体积的人不必再花一轮。
- ★ **`presentAs('ptc')` 是 per-AGENT 的呈现切换**（作用于调用它的 agent 的整个工具上下文、返回 disposer），因此**"部分工具 ptc、其余 native"不可表达**：要 ptc 就是**整批** ptc。`defer` 与 `ptc` 在本仓实现中也不可并存（多 pack 声明不同 mode ⇒ 具名 `unapplied`，不猜）。

> **历史引用声明（G5 H3）**：本卷提到的 `vibe-math-v2`／`v3`／`v4`／`v5`／`v5r` 路径与行号均为**历史源码引用**；这些 preset 已归档到 `archive/legacy-presets/`，不再作为可安装 preset 发布。

**补充（ROUND 36 / F-3）：关掉一场会，不是"服务面归档一下"——durable 的 `live` 行也必须被关掉。**
真机 run 36 的 `VibeMath/vmu/state.json` 第 182 行：`close` 的回执写着 `closeSemantics:"service-archives"`、

①`vibe-math-vmu/kernel/meetings.js:2012` 的 `snapshot()` 现在**剔除**"archive 已记录为 closed"的 live 行
（计数 `counters.droppedLiveWhileArchived`）——一份状态不可能同时说"已关"和"开着"，写穿不许多带一个孪生；
②`meetings.js:2052` 的 `restore()` 在 hydrate 时同样剔除（同一 fold 里 archive 优先，回执带

只加不改、archive 优先、**永不删本地**），并在 `kernel/index.js:1498` 的 `meetings` 适配器上声明

**补充（ROUND 36 / F-4）：日志的"作者"必须由写的人说出来，否则状态板认不出它。**

**补充（ROUND 36 / F-1）：一个先启动的内核，永远读不到别人后来写下的卡——除非它在读之前再看一眼持久层。**
run 36 的所办（先启动）调 `vibe_v5_verified_promote{card:"p-odd-sum"}` 得到 `VMU_NO_SUCH_OBJECT "unknown record:
p-odd-sum"`、`hint:"known ids: (none)"`，而成员子会话 `vibe_v5_read_library` 读得到同一张卡。根因是
`kernel/index.js:1946` 的 `recordsHydrated` 一次性闩锁：第一次成功读到 store 之后，这个内核再也不会看 store。
修法两层（缺一不可）：`kernel/records.js:413` 的 `attachStore(store)`（鸭子类型，不抛，boot 不允许因可选端口崩）
＋ `:929` 的 `synchronize(...)` 在 `get/list/history/externals` **读前**与 `put/supersede` **写前**按 stamp 增量同步
（写前同步是因为 `snapshotRecords` 是整数组覆盖写，只修读路径会留下 lost update）；`:917` 的 `putInternal` 在任何
包装之前捕获（否则恢复 N 行 = N 次全量 `store.write`）；`status().shared` 让"为什么这实例什么都没看见"可自证。
规则：store 未 open / 坏行 ⇒ 计数并具名、不抛不静默；已存在的 id **绝不覆盖**；fold 未变时按签名短路；**读从不写**。
判据在 `tests/vmu-run36-records-shared.test.mjs`（37/0；seam 短路时复现真机原话）。

**补充（ROUND 36 / F-2）：`## 正文` 是正文的**起点**，不是它的边界。**
run 36 里蓝图草案 r-23（4134 B，含 `## 一`～`## 六`）被 adopt 成 r-29 后只剩 939 B，一～六节全丢且
`bodyTruncated:false`。机制：`packs/v5r/blueprint.js` 的 `composeBlueprintBody` 写 `## 正文` 段，而共享
`parseBody` 按 `## ` 切段 ⇒ 收到的正文在草案自己的第一个二级标题处被切开，adopt 又原样搬过去。
现在 `blueprintTextOf(body)`（`packs/v5r/blueprint.js:92-113`）把 `## 正文` 行之后**到 body 末尾**逐字取出；
`blueprintMeans()` 给出四句口径（`status` 只读表头、`history` append-only、`revisions` 与 `currentRevision` 两把尺、
`text` 是正文）。判据在 `tests/vmu-run36-blueprint.test.mjs`（42/0）与 `tests/vmu-blueprint.test.mjs`（54/0）。

**补充（ROUND 37 / F-6）：一场会关掉以后，读面必须还能**找到**它——「不存在」和「已归档」是两件事。**

run 37 的所办关掉 `m1` 之后，`vibe_vmu_meeting{action:"status", id:"m1"}` 得到的是"没有这场会"的拒绝，而
`summary` 明明答出了 `state:"closed"`——同一件事三个读面三种答案（`read_library` 里也还在）。机制：`close()` 把会议
移进 service ARCHIVE（`kernel/meetings.js` 的 `archive`），而 `status` 只经 `meetingView` 解析**活行**，归档 id 于是落到
`noSuchMeeting`。

现在（三处都在读面，写面未动）：
- `kernel/meetings.js` 新增 `archivedIds()`（排序后的归档 id，纯读，不清理）；
- `tools/meeting.js` 的 `status`：解析不到活行时**先查归档**，命中回 `{ state, archived:true, summaryAvailable:true,
  hint:"read it with summary" }`——答案指名记录现在在哪儿，而不是说它从未存在；
- 同文件 `list` 新增 `archivedMeetings` 栏（与 `serviceMeetings` 并列；归档 id 不计入活行）。

判据：`tests/vmu-run37-meeting-archive-reads.test.mjs`（17/0）——真开会→关会→`status` 答 `closed`/`archived`、
`summary` 仍答、`list` 列归档且不算活行、从未开过的 id 仍具名拒 `VMU_NO_SUCH_OBJECT` 且 hint 点名两个注册表。
