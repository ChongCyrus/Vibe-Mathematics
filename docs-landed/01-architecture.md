# 01 · **架构：一次运行由什么构成**

> ★ **一句话**：★ **能力在内核，★ 运行逻辑在 pack，★ 装配在宿主。** ★ 三层不许互相越界。

## 1. ★★★ 三层模型

```
┌─ 宿主（DSH）─────────────────────────────────────────────────────────┐
│  提供：会话、工具注册、子代理、提示词注入点、设置读写、持久化根       │
└───────────────────────────┬─────────────────────────────────────────┘
                            │  vibe-math-vmu/vibe-math-vmu.js  host*.js
                            │  （★ 装配：把这些能力接到内核与面上）
┌───────────────────────────▼─────────────────────────────────────────┐
│ ★ 框架  vibe-math-vmu/                                              │
│    kernel/  103 个模块  …… 能力。它**不认识**"院士""研究员"，只认识【槽位与权限】│
│    tools/   …… 54 个工具面：模型能调用的动词                        │
│    settings/schema.js ……【声明】可设什么（1232 键：类型/域/默认/归属）│
└───────────────────────────┬─────────────────────────────────────────┘
                            │  pack loader（★ 装载/卸载是原子的）
┌───────────────────────────▼─────────────────────────────────────────┐
│ ★ 整合包  packs/<名字>/                                             │
│    settings/      …… 这个机构想要的【值】（数据，不是代码）          │
│    middleware/    …… 这个机构的【策略】（纯函数，或带 api 的模块）   │
│    prompts/       …… 这个机构的【文本】（章、块、人设、语料）        │
│    notices.js     …… 通知/公告的文本与形状                           │
│    index.js       …… 清单：声明上面这些、以及规则与别名              │
└─────────────────────────────────────────────────────────────────────┘
```

★ **换机构 ＝ 换一个 pack 文件夹**，★ **不改内核**（★ 这是第一原则，★ `packs/institute-min/` 就是它的证明：★ 一个八十多行的纯数据清单，★ 就能定义出**另一种机构**）✓

## 2. ★★★ 内核不认识机构语义（D5／D6）

★ **内核只见"槽位（slot）＋权限（permission）"**。★ 例：
```js
slots: [
  { id: 'chair',    label: '主持人', capacity: 1,  permissions: ['convene','close','assign','grant','freeze'] },
  { id: 'member',   label: '成员',   capacity: 0,  permissions: ['speak','vote','propose'] },
  { id: 'temp',     label: '临时',   capacity: 12, permissions: ['speak'] },
]
```
★ 内核只回答"这个槽位能不能 `convene`"，★ **永远不回答"院士能不能"** ✓
★ **好处**：★ 同一份内核可以跑"学术院"（★ `v5r`）／★ "最小机构"（★ `institute-min`）／★ 你自己想的任何机构 ✓
★ **代价（必须承认）**：★ 内核**无法**替你做"院士才能主持"这类判断 —— ★ **那是 pack 的规则或中间件的事** ✓

## 3. ★★★★ 一次成员回合里发生了什么（这是运行的核心）

```
你（主代理/所办）               框架                          成员
     │                            │                             │
     │  vibe_vmu_turn {op:'step'} │                             │
     ├───────────────────────────>│                             │
     │                            │ ① 选下一个该行动的成员      │
     │                            │ ② 装配他的提示词：          │
     │                            │    facts → charter → 契约   │
     │                            │    → pack 段 → override     │
     │                            │ ③ 注入本轮状态块            │
     │                            │ ④ 交给【投递接缝】          │
     │<── awaiting + memberPrompt ┤(★ caller 模式)              │
     │                                                          │
     │  ★ 你按该提示词【以该成员身份作答】                       │
     │  ★ 这是【真】作答，不是占位符                             │
     │                                                          │
     │  vibe_vmu_turn {op:'step', reply:"<成员回复 JSON>"}       │
     ├───────────────────────────>│                             │
     │                            │ ⑤ 把回复记为成员的判断/发言 │
     │                            │ ⑥ 跑中间件（规则/模块）     │
     │                            │ ⑦ 记录、计数、必要时拒绝    │
     │<── 结果 + 状态 ────────────┤                             │
```

★ **★ 关键**：★ **成员回合由【调用会话】扮演**（★ `deliverMode: 'caller'`）。★ 这不是偷懒：★ 实测证明宿主**不提供**一个插件可合法构造的"当前 Agent"对象（★ 它的 `agents.list()` 只返回 **id 字符串**，★ 而请求契约要求一个带 `options`/`session.header` 的对象）⇒ ★ **一次性子代理路径在插件侧【结构性不可用】** ⇒ ★ 于是有了这个诚实的通道 ✓
★ **判据**：★ 返回值里 **`deliveryPath:'caller'` ＋ `awaiting:true` ＋ `memberPrompt`** ✓

## 4. ★★★★★ 结题判据（★ 唯一）

```js
vibe_vmu_status  ⇒  closureVote: {
  cast: true,            // ★ 结题 = 全体有表决权者一致判为已解
  for: ['m2','m3'], against: [], missing: [], eligible: ['m2','m3'],
  permission: 'vote', reason: null
}
```
★ **`cast === true` 才算结题**；★ **不是"看起来收敛"**、★ **不是"没人反对"** ✓
★ 而 **`eligible: []` 时 `cast` 必然 `false`**，★ 且 `reason` 会**明说原因与下一步**：
★ *"no member holds the closure-vote permission, so unanimity is unreachable - seat members with `vibe_vmu_control { action: 'hire', … }`"* ✓
★ **★ 这条设计很重要**：★ **"不可达"和"未通过"是两件事**，★ 而这个字段把二者分开了 ✓

## 5. ★★★ 提示词的顺序（★ 五段式，不许乱）

| ★ 段 | ★ `range` | ★ 内容 | ★ 谁定 |
|---|---|---|---|
| ★ 事实 | ★ `facts` | ★ 名册、票数、对象存在与否 | ★ 内核 |
| ★ 章程 | ★ `charter` | ★ 机构的规章与角色文本 | ★ pack |
| ★ 契约 | ★ `contract` | ★ 通用行为约束 | ★ 内核 |
| ★ pack 段 | ★ `pack` | ★ 本机构的其他文本块 | ★ pack |
| ★ override | ★ `override` | ★ 部署者的最后覆盖 | ★ 宿主 |

★ **绑定优先级**：★ `role` → `phase` → `member` → `task` → `agent` ⇒ ★ **同段多绑定命中时取优先级最高的一条**（★ 每个段在每次装配里**只出一个赢家**）✓
★ **模板变量白名单**（★ 内核拥有）：★ `member`／`role`／`roleLabel`／`phase`／`roster`／`quorum`／`round`／`statusBlock`／`time`／`task`／`pack`／★ 以及带参的 `setting:`（★ 如 `{{ setting:vmu.turn.instituteName }}`）✓
★ **不在白名单的变量一律报错**（★ 不许静默渲染成空）✓

## 6. ★★★★ 零机制：默认什么都没开

★ **默认是"零注入/零机制"**：★ 不声明 ⇒ 没有会议、没有票箱、没有汇报、没有中间件 ✓
★ **每个"动起来"的东西都必须来自【声明】**：★ 一个 `settings` 键、★ 一个 pack 清单条目、★ 或一次工具调用 ✓
★ **连"读"也遵守**：★ 零配置下读面**正常作答**（★ 返回空集而非报错），★ 因为"读得到空"和"读不了"是两件事 ✓
★ **例**：★ `vibe_vmu_wait` 在零限速时报 **`unlimited:true`** ＋ 一句 *"this call was NOT limited"* —— ★ **它明说自己没在保护你**，★ 而不是假装限过 ✓

## 7. ★★★ 状态与耐久

| ★ 层 | ★ 在哪 | ★ 谁的 |
|---|---|---|
| ★ 会话内状态 | ★ 内核的 Map | ★ 进程 |
| ★ 耐久折页 | ★ `kernel/store.js`（★ 一个 `root` ＋ 白名单键） | ★ 宿主给根，★ 白名单由 store 拥有 |
| ★ 恢复 | ★ `kernel/resume.js`（★ **读之前不许写**） | ★ 同上 |

★ **两条硬规矩**：★ **① 读成功之前不许写**（★ 否则会在"没读过的状态"上覆写）；★ **② 读不了的折页【不当作空的】**（★ 它按名拒绝，★ 并说明 *"refusing to treat an unreadable fold as an empty one"*）✓

## 8. ★★ 一图总结

★ **自由度在哪**：★ pack 里的一切（★ 文本／值／策略／规则）都是**数据或纯函数**，★ 换掉它不改一行内核 ✓
★ **可调控性在哪**：★ **1232 个设置键**（★ 以 `settings/schema.js` 的生成表 `docs/04-settings.md` 为准：**1138 已接线、94 已声明未接线**），★ 每个都有类型、域、默认、归属与冷热级别 ✓
★ **可定义性在哪**：★ 同一份内核 ＋ 不同 pack ＝ **不同的机构制度** ✓
★ **扩展性在哪**：★ 中间件可写**纯函数**（★ 声明式规则 M1）或**带 `api` 的模块**（★ M2，★ 能触达服务）；★ **再往上还有 M3 子进程脚本与 M4 插件**（★ 见 `03-extending` §2）；★ 工具面本身也由声明驱动注册 ✓
